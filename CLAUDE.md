# CLAUDE.md

## Role

You are acting as a systematic futures researcher and quant developer helping build a
production-style research platform, not a coursework project. Every design choice should
be defensible in front of a Portfolio Implementation Analyst / systematic macro desk
interview, not just "does it run."

## Project identity

**Target state (the resume bullet — this is where the project is going, not where it is):**

> Systematic Commodity & Macro Futures Research Platform: Developing a systematic futures
> research framework across 42 markets spanning commodities, FX, rates, and equities;
> researching trend, breakout, short-term reversal, and relative-value signals with
> volatility targeting and portfolio optimization, while building infrastructure for live
> data ingestion and paper trading.

This repo is one of **two related, separate projects**:

1. **This project (Commodities/).** The CTA platform itself — 42-market universe, signal
   research, portfolio construction, eventually live/paper trading. Consumes external
   signals; does not itself scrape AIS data or build congestion indices.
2. **Port Congestion Market Signals** (separate repo — `Projects/Port Congestion Market
   Signals/`). Builds an AIS-derived port congestion signal and tests whether it predicts
   commodity-linked asset prices. Its Track A/C targets are **WTI and Brent**, and its
   Track B target is a **9-commodity basket (Corn, Soybeans, Wheat, KC Wheat, Copper,
   Coffee, Sugar, Cocoa, Cotton)** — all 11 of these are already members of this
   project's 42-asset universe. See "Integration with the port congestion project" below.

There is also a **third, retired project**: a 13-instrument Cross-Asset Statistical
Arbitrage Engine (commodity futures + US sector ETFs, mean-reversion/cointegration/
momentum via a turnover-penalized mean-variance optimizer). That project is **archived,
not being extended**. It is referenced here only because its architectural pattern
(Book/Allocator, pure-function alphas, a frozen regression baseline) is worth reusing —
see "Architecture" below. Its specific mechanics (Fama-MacBeth alignment, DCC-GJR
crowding regimes) were solving a small-cross-section, mean-reversion-specific problem and
should **not** be ported as-is.

## Hard rules (from real, already-found bugs — do not repeat these)

1. **Never edit the asset universe after observing backtest performance.**
   `feature_engineering.ipynb` currently drops Natural Gas and then all of Energy *after*
   seeing they hurt the Sharpe ratio — a real, live instance of this mistake, not a
   hypothetical. Fix forward: decide inclusion rules (e.g. liquidity/ADV-based) before
   looking at performance, or move to a formal train/held-out split before drawing any
   conclusion that changes the universe.
2. **Never run a stationarity or cointegration test on the full sample.**
   `Time_Series_Models.ipynb` runs Engle-Granger cointegration on the entire history —
   this is the *exact* look-ahead bug the retired stat-arb project's own dossier
   documented finding and fixing. It came back because the lesson lived in a PDF, not in
   reusable code. Always use a rolling or expanding window with a strict train/test
   boundary for any statistical test used to select or size a trade.
3. **Always `shift(1)` a signal before using it to trade "today."** Every backtest
   function in this repo already does this correctly (`positions = positions.shift(1)`)
   — keep doing it in every new signal/backtest path, including any port-congestion
   feature merged in later.
4. **Don't fake carry with a residual-return proxy if term-structure data isn't
   available.** Label the signal missing/blocked instead. This is what the retired
   project did right (it removed a mislabeled carry signal rather than keep it) — it's
   why carry was honestly marked blocked here rather than silently wrong, until a free
   term-structure source was found and live-verified (see `WORKFLOW.md` Phase 4). The
   principle still applies going forward: if that source turns out to be unreliable on
   closer validation, mark it blocked again rather than patch around it.
5. **Binary signals have already been shown to underperform continuous, vol-scaled
   signals in this universe** (`feature_engineering.ipynb`'s own conclusion: "binary
   momentum signals are a disaster"). Don't re-litigate this without new evidence; build
   every new signal family (breakout, crossover, RV z-score) continuous/vol-scaled from
   the start.
6. **Reuse Book/Allocator as an architectural pattern once a second signal family
   exists — not before.** One signal family in one notebook is appropriately scoped, not
   under-engineered. The moment a second family lands, stop copy-pasting the backtest
   function with small variations — this already happened once (two slightly different
   `backtest_signal` definitions existed in `feature_engineering.ipynb`, fixed 2026-07-14
   by extracting `src/signal_lib.py`) — and extract shared logic into real
   functions/modules. (Portfolio-construction scaffolding — `src/portfolio/` — was built
   2026-07-15 ahead of this trigger as a deliberate, logged exception: porting an
   already-evaluated engine, not guessing at a shape from scratch. See `cleanup.md`
   section 3 and `WORKFLOW.md` Phase 5. Not a precedent for skipping this rule generally.)
7. **Re-derive signal mechanics per strategy family — don't port stat-arb-specific
   mechanics onto trend/breakout/RV.** No forced Fama-MacBeth alignment for a per-asset
   time-series signal like momentum or breakout. No DCC-GJR "crowding" regime logic that
   assumes crisis hurts the strategy — trend-following is documented to have the opposite
   property ("crisis alpha").

## Architecture

Reuse the retired project's **shape**, not its mechanics:

- A `Book` should eventually own one signal family's alpha, covariance, optimizer
  parameters, and vol target end-to-end — self-contained, independently testable.
- An `Allocator` should eventually combine Books and apply any regime conditioning
  *before* the optimizer runs, never after (vol targeting silently cancels out any
  post-solve position scaling — this is a documented lesson from the retired project, not
  a guess).
- Alpha modules should be pure functions with no optimizer dependency, same pattern as
  the retired project's `engine/alphas/`.
- What does **not** transfer: Fama-MacBeth cross-sectional alignment (trend/breakout are
  per-asset time-series problems, not cross-sectional ones — they don't need conversion
  to expected-return units the way a 13-name mean-reversion book did), and DCC-GJR
  "crowding" regime detection (assumes crisis hurts the strategy — the opposite of
  trend-following's documented crisis-alpha property). Any regime overlay for this
  project needs to be re-derived, not ported.

Don't build this yet — it's Phase 5+ in `WORKFLOW.md`. Noted here so early signal code is
written in a way that won't fight this shape later (e.g., keep alpha construction as pure
functions returning `(T × N)` DataFrames now, even inside a notebook).
